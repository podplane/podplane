# Podplane Provider

This provider is used only by OpenTofu/Terraform configuration generated by the Podplane CLI. It is not intended for hand-written configurations. This page documents the provider contract for maintainers.

The Podplane OpenTofu/Terraform provider:

- creates an in-memory Netsy bootstrap snapshot from a Podplane seed using Podplane's `netsyseed` package, then uploads it to S3 or GCS as `bootstrap.netsy` using native cloud SDKs and create-only preconditions. Completed uploads can be adopted after an interrupted apply; existing Netsy state is never overwritten.

- renders Podplane VM userdata from pinned vmconfig manifest JSON using the same canonical Go template used for local clusters in the Podplane CLI.

- creates or adopts the dedicated workload CA key through a state-safe resource that never places private key bytes in configuration or state.

- creates or adopts Nstance's separate registration signing key and injects a short-lived operator nonce and public CA directly into a cluster-specific seed, without transporting credentials through OpenTofu/Terraform or Helm values.

## Data sources

`podplane_userdata` renders auditable userdata during planning without network or filesystem access inside the provider:

```hcl
data "podplane_userdata" "knc_arm64" {
  manifest_json                 = file("${path.module}/podplane.cluster.vmconfig.knc.arm64.json")
  deps_mirror_url               = "https://deps.podplane.dev"
  provider_kind                 = "aws"
  aws_account_id                = data.aws_caller_identity.current.account_id
  immutable_ssh_authorized_keys = var.immutable_ssh_authorized_keys
  enable_ssm                    = var.enable_ssm
}
```

The manifest and rendered content are intentionally retained in OpenTofu/Terraform state. Mutable runtime configuration, including `SSH_AUTHORIZED_KEYS`, is not rendered into userdata.

Nstance Server `nst` instance manifests accept a non-secret `server_env` string map for userdata.

## Resource contract

### Workload CA Key

`podplane_workload_ca_key` creates or adopts exactly one unencrypted PKCS#8 Ed25519 key at the canonical name derived from `secrets_provider` and `key_prefix`:

- `aws-secrets-manager`: `/<key_prefix>/workload-ca-key`
- `aws-parameter-store`: `/<key_prefix>/workload-ca-key` as a `SecureString`
- `google-secret-manager`: `<key_prefix>_workload-ca-key` in `project`

For AWS, `region` and `profile` can select the SDK configuration to use. For Google Cloud, `project` identifies the project in which the secret is stored. Externally administered Vault and OpenBao installations are outside this resource's scope; customers provision their workload CA key before creating the cluster.

Set `secrets_provider` to select the cloud secret backend: `aws-parameter-store`, `aws-secrets-manager`, or `google-secret-manager`.

The resource is designed to keep the private key out of OpenTofu/Terraform state. It generates the key inside the provider and writes it directly to the selected secret backend. OpenTofu/Terraform records only enough information to recognize the key later: its backend location, backend version, and public-key fingerprint.

The workload CA key is a long-lived cluster identity, so the provider will not silently replace or rotate it. During creation it uses the backend's create-only operation. If another provisioning process created the same key first, the provider adopts that key after checking that it is a valid Ed25519 private key. On later refreshes, it reads only secret metadata and reports an error if the key has disappeared or its current version has changed. Recover the original version instead of recreating the resource if this happens.

Changing any resource argument requires VM replacement, but automatic key replacement is intentionally unsupported. Import is also unsupported. Removing the resource from configuration removes it from OpenTofu/Terraform state without deleting the key from the secret backend; retiring or rotating a workload CA must be an explicit operational procedure.

Google Secret Manager creates a secret and its first version in two separate operations. If provisioning is interrupted between them, an empty secret can remain. The provider will not add a key to that existing empty secret because another provisioning process could still be using it. Confirm that no other provisioning process is active, delete the empty secret manually, and apply again.

### Nstance registration signing key

`podplane_nstance_registration_key` uses Nstance v2's PKCS#8 Ed25519 contract, independently of the workload CA:

| `secrets_provider` (same as Nstance `cluster.secrets.provider`) | Backend name |
| --- | --- |
| `aws-parameter-store` (default) | `secret_prefix` + `registration-nonce.key`, a SecureString |
| `aws-secrets-manager` | `secret_prefix` + `registration-nonce.key`, binary secret data |
| `google-secret-manager` | `projects/<project>/secrets/` + `secret_prefix` + `registration-nonce-key` |

`secret_prefix` is the exact Nstance secrets prefix, including any trailing separator. Unlike the workload CA resource, this resource does not insert separators. Google requires `project`; AWS accepts `region` and `profile`. The cloud service encrypts the PKCS#8 payload at rest and decrypts authorized reads. Nstance's optional client-encrypted `object-storage` secrets backend is not supported by this resource; configure one of the cloud backends above. Do not wrap cloud secret payloads in Nstance's object-storage encryption envelope.

Create uses backend create-only operations and adopts the winner if Nstance, another apply, or an earlier interrupted apply already created it. OpenTofu/Terraform stores the backend identity in `id`, the immutable `backend_version`, and the SHA-256 PKIX public-key `public_key_fingerprint`, plus non-secret configuration. Refresh reads metadata only and fails closed on key loss/version changes. Update never rotates the signer, and destroy retains it. An existing empty Google secret is handled with the same manual recovery procedure as the workload CA key.

The CLI generates the signer and seed bootstrap references when the AWS/Google `platform` or `agentic` overlay enables the Nstance operator. Infrastructure must be ready before signer creation, and Nstance-server VM creation must not depend on seed completion: the provider waits for the server to publish its CA.

### Kubernetes ServiceAccount signing key

`podplane_service_account_key` creates a PKCS#8 ECDSA P-256 signer (ES256) in
Nstance's cloud secret backend, independently of the workload CA and registration
signer. Existing P-256 and RSA signers are adopted without rotation. P-256 is the
strongest ECDSA curve supported by both Kubernetes and Google STS. Local clusters
also generate P-256 signers and retain existing keys.

Inputs are `secrets_provider`, `secret_prefix`, and the same provider-specific
`region`, `profile`, or `project` settings as the registration key. The source name
is `service-accounts.key` (Google stores it as `<secret_prefix>service-accounts-key`).

Only `id`, `backend_version`, `public_key_pem`, and `jwks_json` enter state alongside
the configuration. The private key never enters OpenTofu/Terraform state, Helm values, 
user-data, or the Netsy seed. Refresh checks metadata; destroy retains the key. An
existing empty Google secret requires manual recovery, as above.

All cloud clusters provision this signer, including bare clusters. Nstance delivers
the private key and a separate PEM verification-key file only to control-plane (`knc`)
nodes. Google federation receives the public JWKS before Kubernetes starts; its
key IDs match kube-apiserver's SPKI SHA-256 convention. Google IAM JSON keys are
not needed for Zot, the operator, or the GCP CSI provider.

Automatic rotation is not implemented. Future rollover must first publish both old
and new verification keys to kube-apiserver and Google, then switch the active
private key, and retain the old public key until issued tokens expire. Keeping
signing and verification material separate permits that overlap without changing
the file or federation contracts; reconfiguration currently requires kube-apiserver
restarts.

### Netsy seed

`podplane_netsy_seed_s3`:

- `cluster_config_path`
- `seed_path`
- `values_content` (optional inline YAML or JSON)
- `values_file` (optional user-authored YAML or JSON file)
- `bucket`
- `prefix` (optional)
- `region`
- `profile`
- `nstance_bootstrap` (optional non-secret operator bootstrap references)

`podplane_netsy_seed_gcs`:

- `cluster_config_path`
- `seed_path`
- `values_content` (optional inline YAML or JSON)
- `values_file` (optional user-authored YAML or JSON file)
- `bucket`
- `prefix` (optional)
- `project`
- `nstance_bootstrap` (optional non-secret operator bootstrap references)

The provider:

- generates snapshots in-process using Podplane's `netsyseed` package
- resolves `cluster.seed.name`/`version` from the published seeds manifest and verifies the file against `cluster.seed.digest`; `seed_path` may point to a custom Podplane seed file
- merges values with precedence: provider-derived defaults < `values_content` < `values_file`
- adopts a completed bootstrap with matching non-secret input identity before accessing keys or generating credentials; otherwise fails if the target prefix already contains Netsy state
- uploads with S3 `If-None-Match: *` or GCS `DoesNotExist` preconditions so existing Netsy state is never overwritten
- requests S3 AES-256 server-side encryption; GCS uses its built-in encryption at rest (including bucket-default CMEK)
- records only the S3 object version/ETag or GCS generation in `object_version`; refresh reads metadata, not snapshot payloads or keys, and reports loss/version changes without triggering repair

Every seed resource represents a snapshot and refresh verifies its recorded object version. For bare clusters, the CLI omits the seed resource entirely. Existing snapshots without a matching completion marker cannot be adopted; never replace a live cluster's snapshot to work around this check.

Seed resources create the initial state for a new cluster. After Netsy has been initialized, changing a seed setting will not overwrite its existing data. To reconfigure components in a running cluster, update their live values instead.

Cloud credentials are resolved by the native SDKs. AWS uses the standard AWS SDK chain, optionally scoped by `region` and `profile`. GCS uses Application Default Credentials, optionally scoped by `project` for quota/billing.

## Releases

One `v*` tag in [podplane/podplane](https://github.com/podplane/podplane) builds both the `podplane` CLI and `terraform-provider-podplane` binaries from the same commit. `.github/workflows/release.yaml` publishes the provider through [podplane/terraform-provider-podplane](https://github.com/podplane/terraform-provider-podplane), then the CLI and Homebrew formula to [podplane/homebrew-tap](https://github.com/podplane/homebrew-tap). The provider is self-contained; OpenTofu/Terraform runners do not need the CLI. The [podplane/terraform-provider-podplane](https://github.com/podplane/terraform-provider-podplane) repository has no separate implementation or release workflow. This file is published there as `docs/index.md`.

### Versions

Historically the `podplane` and `terraform-provider-podplane` binaries had separate release pipelines, each using different major version (`0.x.x` and `1.x.x` respectively). When these two pipelines were brought together into one, the decision was to aim for long-term uniformity, with a short-term (pre-`2.x.x` release) mapping.

`internal/buildvars.ProviderVersionFor` supplies the mapping:

| CLI version | Provider version |
| --- | --- |
| `dev` | `0.0.0-dev` (local only) |
| `0.m.p`, with `m < 900` | `1.(100+m).p` |
| `1.m.p` | `1.(1000+m).p` |
| `2.m.p` and higher | unchanged |

Offsets avoid existing immutable provider tags. Prerelease suffixes are preserved; release tags require canonical SemVer prefixed with `v`, without build metadata.

### Publication and recovery

Releases include Linux/macOS amd64/arm64 and Windows amd64 ZIPs, licenses, SPDX SBOMs, GPG-signed SHA-256 checksums, Cosign-signed SHA-512 checksums, and `release-metadata.json` identifying the source commit, tag, and mapped version. Signed checksums cover release metadata and the registry manifest.

`scripts/tf-provider-release.sh` has read-only `metadata` and `check` modes; **`publish` writes to Git and GitHub**, so never use it for local validation. It updates docs, manifest, and release metadata, atomically pushes the publication commit and tag, and publishes a draft only after all assets upload. Reruns verify and reuse an existing public provider release before continuing with the CLI; they never overwrite it. Collisions, corrupt releases, and existing drafts stop for manual recovery. After partial failures, check the CLI release and Homebrew tap too. Never move published tags or replace assets to force a retry.

## Local Development

From the **Podplane source repository**, build both binaries and explicitly select the local provider for CLI-managed OpenTofu/Terraform commands:

```sh
make build
export PODPLANE_TF_PROVIDER_DIR="$PWD/bin"
./bin/podplane cluster create --cluster-config /path/to/podplane.cluster.jsonc --no-apply
```

`make build-cli` and `make build-provider` build individual targets. Rebuild both after shared-code changes. The CLI inserts development overrides into a private per-command configuration, preserving its provider mirror; it does not edit the shared cache configuration or your home-directory configuration. Unset `PODPLANE_TF_PROVIDER_DIR` to stop overriding. Use disposable development clusters: development providers can change OpenTofu/Terraform state incompatibly.

Untagged builds report `0.0.0-dev`. Their generated HCL allows a published provider for `init` and lock-file bookkeeping, but **plan/apply use the local binary when the override is set**. Initialization may still download published dependencies; no new Podplane/provider release is needed. Development overrides do not supply external cloud credentials or infrastructure.

When running OpenTofu/Terraform directly rather than through Podplane, use an explicit `TF_CLI_CONFIG_FILE` containing the following, with an absolute source-tree `bin` path:

```hcl
provider_installation {
  dev_overrides {
    "registry.terraform.io/podplane/podplane" = "/absolute/path/to/podplane/bin"
    "registry.opentofu.org/podplane/podplane" = "/absolute/path/to/podplane/bin"
  }
  direct {}
}
```

The override path is the directory, not the binary itself. Development-override warnings from OpenTofu/Terraform are expected. The `PODPLANE_TF_PROVIDER_DIR` environment variable is interpreted only by the Podplane CLI, not by OpenTofu/Terraform itself.
